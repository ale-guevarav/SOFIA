	\begin{abstract}
		SOFIA is a modular kinetic surface that responds to the gestures of a user. This work presents its graphical user interface (GUI): the window that shows the camera, controls the gesture detection, and sends each recognized gesture to the robot or to its simulation. The GUI runs the video processing and each communication link in separate threads, so that it never freezes. Its behavior is explained with three state machines: the processing thread, which can be started, paused, resumed, and stopped; the reliable sending of commands, with acknowledgements and retransmission; and the link supervision. The same commands can be sent to the robot, to a Webots simulation, or to both at the same time, which turns the simulation into a digital twin of the robot. The GUI also aligns the robot: a second camera measures the tilt of every unit, and the GUI computes and sends a new zero for each servo, unit by unit, in a closed loop. In an automatic test against the simulated robot, all commands were acknowledged with 3\,\% losses and 2\,\% damaged bytes, none was executed twice, and the link recovered by itself from every interruption.
 \end{abstract}

	\begin{IEEEkeywords}
		Graphical user interface, multithreading, state machines, communication protocol, gesture recognition, Webots, digital twin, alignment.

	\section{SOFIA in Brief}

	SOFIA is an interactive installation made of 16 hexagonal units in a honeycomb arrangement; each unit can tilt in two directions \cite{sofia_architecture}. It has four parts: (i) a \emph{vision system} that watches the user with a camera and recognizes five gestures (INICIO, RECARGAR, ESCUDO, ATAQUE, and FIN) or follows the position of the right hand, using MediaPipe \cite{lugaresi2019mediapipe}; (ii) the \emph{GUI}, which shows the result and controls the system; (iii) a \emph{robot controller}, which receives commands through a wireless link and moves the units; and (iv) a \emph{simulation} of the 16 units in Webots \cite{webots}, which can play the role of the robot. This paper is about the GUI and how it talks to the robot and to the simulation.


	\section{Architecture}

	The GUI was built with PySide6 \cite{pyside6}, the Python version of Qt, because it provides threads that are integrated with the interface (\texttt{QThread}), signals to pass data between threads safely, and a way to pause a thread without consuming CPU. Fig.~\ref{fig:arq} shows the threads. The \emph{GUI thread} only draws the window and handles the buttons. The \emph{vision thread} reads the camera and runs the detection, which takes tens of milliseconds per frame. Each \emph{link thread} talks to one target, the robot over Bluetooth Low Energy \cite{bleak} or the simulation over a local TCP socket, because waiting for an answer may take from milliseconds to seconds. Another thread receives the images of a virtual camera of the simulation, and an \emph{alignment thread} exists only while the robot is being aligned (Section~\ref{sec:align}). Threads never touch the widgets: they send their results to the GUI thread through Qt signals.

	The window has the video on the left and, on the right, the controls in the order in which they are used: detection (start, pause, resume, stop, the pose camera, and the \emph{Alignment} menu), mode, result, targets (robot and simulation), and an event log with every command sent and its answer. The cameras are listed by the name the operating system gives them (for example, the model of the webcam) and only if they are connected, so the user cannot pick a missing camera or the same one for the user and for the robot. There are three modes: \emph{game}, where each new gesture is sent once; \emph{tracking}, where the position of the right hand is sent continuously; and \emph{test}, where the GUI asks the user for gestures and measures how often and how fast they are recognized. The image is shown as a mirror, as in a selfie; since the detector names the hands for a non-mirrored image, the GUI swaps them, so that tracking follows the real right hand and ignores the other one.


	\section{The Processing Thread}

	The vision thread follows the state machine of Fig.~\ref{fig:worker}. \emph{Start} creates the thread, which opens the camera and loads the models (LOADING) and then processes frames (RUNNING). \emph{Pause} makes the thread wait on a condition without using the CPU, with the camera still open; \emph{resume} wakes it up. \emph{Stop} ends the loop, releases the camera, and sends a STOP command to the robot. Any error, such as a camera that cannot be opened or that stops sending frames, also leads to STOPPED with a message in the window, instead of closing the application. The buttons are enabled according to the state, so only valid transitions can be requested.

	\section{Talking to the Robot}

	\subsection{Messages}

	Each message is a short frame: a start byte (\texttt{0xA5}), the type, a sequence number, the payload length, the payload (0--14 bytes), and a CRC-8 checksum that detects damaged frames. The messages are listed in Table~\ref{tab:msg}. A gesture is sent with POSE only when it changes, and the hand position with TRACK up to 20 times per second; TRACK is not acknowledged, since a newer position replaces an older one. ADJUST (type \texttt{0x05}, 6 bytes) carries the unit, a flag that asks the unit to settle with a short shake, and the new zero of its two servos in tenths of a degree; the robot rejects zeros beyond $\pm20^\circ$.

	\subsection{Reliable Sending}

	Every command except TRACK is sent with the state machine of Fig.~\ref{fig:ack}, one at a time. After sending, the link waits up to 300~ms for an acknowledgement that matches the type and sequence number of the command. If it does not arrive, or if the frame arrived damaged (NACK with a CRC error), the command is sent again \emph{with the same sequence number}, up to three times; if all fail, it is reported as failed in the event log. Since the sequence number does not change, the robot recognizes a repeated command whose first acknowledgement was lost, answers it again, and does not repeat the movement.

	\subsection{Link Supervision}

	The link itself follows the state machine of Fig.~\ref{fig:link}. When the user presses \emph{connect}, the GUI searches for the robot and opens the link; on success, it sends the active mode and the 16 zeros saved by the last alignment (ADJUST), which replace the factory zeros of the firmware. While connected, if nothing has been sent for 1~s, the GUI sends a PING (heartbeat), so that the robot can tell a quiet link from a lost one: if the robot receives nothing for 3~s, it moves to a safe position by itself. If the link drops, or the robot stops answering for 3~s, the GUI marks it as RECONNECTING and tries again by itself after 1, 2, 4, and 8~s, and then every 10~s, until it succeeds or the user cancels; the application never closes.

	\section{Simulation and Digital Twin}

	The simulation receives \emph{exactly the same frames} as the robot, so it also tests the protocol, not only the movements. Since TCP carries a stream of bytes instead of separate packets, each frame is preceded by one byte with its length. A simulated controller in Webots validates and acknowledges the frames with the same rules and moves the 16 simulated units: in game mode, each gesture draws a pattern with the whole array; in tracking mode, the units point at a sphere that follows the hand. A local link never loses frames, so the GUI can optionally add delay ($30\pm10$~ms), losses (3\,\%), and damaged bytes (2\,\%), like a wireless link, to see the retransmissions of Fig.~\ref{fig:ack} in action. A virtual camera above the array sends its images ($320\times320$~px, about 15 per second) through a separate socket and thread, so the user sees, in the same window, the gesture and the response of the simulated array.

	The GUI sends each command to \emph{every} connected target. With only the simulation connected, the whole system can be tested without the robot; with only the robot, it works as usual; and with both, every command reaches the robot and the simulation at the same time, which then works as a digital twin. The event log labels each answer with its target, so both responses can be compared.


	\section{Aligning the Robot from the GUI}
	\label{sec:align}

	The servos are mounted by hand, so a unit commanded to $(0^\circ,0^\circ)$ may be tilted by several degrees. A second camera, the \emph{module camera}, looks at the array from above, and the GUI reuses the visual diagnosis of SOFIA: four ArUco markers rectify the image, and a small convolutional network estimates the two tilt angles of each unit. The \emph{Alignment} menu has two options. \emph{Take zeros} measures the 16 units once and stores the zero of every servo. \emph{Align} corrects, one by one and from the least to the most misaligned, the units that are not within $2^\circ$: it sends ADJUST with the new zero, waits, takes another picture, and repeats until the unit is aligned, up to four times. If an axis gets worse instead of better, the servo is mounted or wired the other way, so the GUI inverts the sign of that axis for that unit only. The zeros and signs are saved in a file that is sent to the robot on every connection.

	Before starting, the GUI shows the module camera live, with the markers it sees, so the user can place it; aligning starts only when the four markers are visible. During the process the GUI sends STOP, stops sending gestures and positions, and shows the analyzed picture and a progress bar in a separate window; if the markers are lost, it warns that there is no SOFIA in view. Like the video processing, the alignment runs in its own thread, so the window remains responsive and the process can be canceled at any time.

	\section{Verification}

	The GUI was tested with the camera and the detection replaced by stubs, applying the controls in sequence: the thread went through LOADING, RUNNING, PAUSED, RUNNING, and STOPPED, and sent no frames while paused. The link was tested automatically against the controller of the simulated robot, using the same link code as the GUI (Table~\ref{tab:ver}). On a clean channel, the 100 gestures were acknowledged in 9.7~ms on average. With the simulated wireless channel, all 300 gestures were acknowledged, 39 of them after a retransmission, and each was executed exactly once; the same held when a new gesture was sent every 100~ms, and when tracking at 20~frames per second was mixed with a gesture every 2~s. When the simulated robot was switched off or stopped answering, the GUI detected it, reconnected by itself in all five repetitions, and the next gesture was acknowledged. A repeated frame was answered twice but executed once, a damaged frame was rejected, and the robot went to its safe position 3.02~s after the GUI went silent. The first run of this test found two errors in the link, which were corrected before the final run.

Pending are the tests with several users and lighting conditions in front of the camera, and the measurement of the time from gesture to movement on the robot.


	\section{Conclusions}

	The GUI of SOFIA keeps the interface responsive by running the video processing and each communication link in separate threads. Its main behaviors are simple state machines: the processing thread (start, pause, resume, stop, and recovery from camera errors), the reliable sending of commands (acknowledgement, retransmission with the same sequence number, and failure report), and the link supervision (heartbeat and safe position). Because the simulation speaks the same protocol as the robot, the system can be developed and tested without hardware and can run a digital twin of the robot. The same window also aligns the robot with a second camera, through a single new message (ADJUST) and zeros that are restored on every connection. Future work includes the tests with several users and lighting conditions, the measurement of the time from gesture to movement on the robot, and replacing the servos that do not reach the commanded angle.
